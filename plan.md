# Plan: IDM documentation website

Status: PLANNING ONLY. This document proposes an approach for a documentation website for
the Interoperability Data Model (IDM). Nothing is built yet. Waiting for approval before
scaffolding the site or adding any deploy workflow.

## 0. Context and what I found in the repo

Branch: this plan sits on `idm-docs-website`, cut from
`dev-9183-sync-interoperability-data-model-to-dcide-app-validators` (the dcide data model
branch that aligns the IDM to the dcide-app validators). That base branch is the right one:
it holds the current, validator aligned schemas, so the docs generate from the freshest
source of truth.

Note on `git fetch`: `git fetch origin` is refused in this checkout because the base branch
is checked out in this worktree and the remote is configured with a broad
`+refs/*:refs/*` refspec, so a plain fetch tries to update the checked out ref. Not a
problem for planning. Before we build, we should fetch with an explicit refspec that skips
the current head (for example fetch only `refs/heads/*:refs/remotes/origin/*`) or run it
from the main worktree.

Repo contents that matter for docs:

- `schema/`: 31 JSON Schema files (draft-07), one per component type, for example
  `schema/battery.json`. These are generated from the dcide-app component validators, the
  source of truth. Each is a self contained schema using a top `$ref` into `definitions`
  and heavy internal `$ref` reuse.
- `examples/`: 31 valid example instances, one per type, for example
  `examples/testBattery.json`.
- `docs/`: 33 hand written markdown pages: `README.md` (index), `common.md` (shared base
  and port model), and one page per component type.
- `README.md`: project narrative (why the IDM exists, background, vision).
- `Schema description 2026.02.12.pdf` and `Creating IDM Product files.docx`: reference
  material, not machine readable.

There is no `schema/common.json`. The shared base (identification, compliance,
communication, environmental, mechanical, performance, files, images, metadata, ports) is
inlined into every component schema and documented once in `docs/common.md`.

Important correction on IEC 62683: the repo does not contain IEC 62683 content or an IEC
62683 mapping. The only IEC references are two fields on `breaker` and `fuse`
(`serviceShortCircuitBreakingCapacityIEC`, `ultimateShortCircuitBreakingCapacityIEC`, that
is Ics and Icu), which cite IEC short circuit ratings alongside their UL counterparts. The
model's stated alignment is to the dcide-app validators and the Emerge Alliance effort, not
to IEC 62683. See open question 1. I will scope the standards page around what actually
exists in the model unless you provide IEC 62683 source material.

## 1. Goal and audience

Goal: publish a browsable, linkable, versioned reference for the IDM so that the JSON
schemas stop being the only readable form of the model. The site should make it easy to
answer "what fields does a converter have, what units, what is required, and how does it
relate to the shared base."

Audiences, in priority order:

- Manufacturers and data authors preparing harmonized datasheets in IDM JSON. They need
  per component field references, units, allowed values, and valid examples.
- Software engineers integrating the IDM (dcide-app and third parties). They need the raw
  schemas, the required fields, enums, and the port model.
- Standards and community contributors (Emerge Alliance and others). They need the model
  overview, the rationale, and a contributing path.

## 2. Framework choice

Requirements that drive the choice:

- Auto generate reference pages from 31 JSON Schemas so docs cannot drift from the source
  of truth.
- Also host hand written prose (the existing `docs/*.md` are good and should be reused).
- Static output deployable to GitHub Pages, no server.
- Low long term maintenance. This is a data model that changes when validators change; the
  site should mostly regenerate itself.

Options evaluated:

- MkDocs Material (Python)
  - Pros: fastest path to a clean docs site; the existing `docs/*.md` drop in nearly as is;
    excellent search and navigation; simple `mkdocs.yml`; large plugin ecosystem. Schema
    reference can be generated by a small Python pre build script (the model is plain
    draft-07 with local `$ref`, easy to walk) or via a JSON Schema plugin.
  - Cons: no first class JSON Schema renderer built in; we own the generation script.
- Docusaurus (React/Node)
  - Pros: powerful, MDX lets us embed interactive components, strong versioning story.
  - Cons: heavier toolchain and more moving parts than this content needs; React knowledge
    to maintain; schema rendering still custom. Over built for a field reference.
- VitePress or Astro Starlight (Node)
  - Pros: fast, modern, nice default theme (Starlight); Markdown/MDX; good DX.
  - Cons: same as Docusaurus on schema rendering (custom); smaller docs plugin ecosystem
    than MkDocs Material for pure documentation needs.
- Redocly / JSON Schema focused renderers (redocly, docusaurus-json-schema-plugin,
  json-schema-for-humans)
  - Pros: purpose built to render schemas into readable reference pages; least custom code
    for the reference section; `json-schema-for-humans` produces standalone HTML/Markdown
    per schema.
  - Cons: Redocly is OpenAPI first, not plain JSON Schema; our files are component schemas,
    not an API spec, so it is an awkward fit. Standalone schema renderers produce reference
    pages but not a full site with guides, so we would still need a site framework around
    them. Best used as a generator feeding a framework, not as the framework.

Operator decision: Fumadocs (Next.js) was chosen and is being built, deployed as a Next.js
static export (`output: 'export'`) to GitHub Pages. This supersedes the MkDocs recommendation
below, which is kept for the record. See section 2b for the Fumadocs rationale.

Recommendation (original, superseded by the Fumadocs decision above): MkDocs Material, with a small schema to Markdown generation step
(`json-schema-for-humans` for a rich per schema reference, or a ~150 line Python script
tailored to this model's shape). Rationale:

- The existing `docs/*.md` are already MkDocs ready, so we keep the good hand written prose
  with near zero rework.
- The schemas are plain draft-07 with predictable structure, so generating Markdown from
  them is straightforward and we avoid a heavy JS build.
- Lowest maintenance and least framework churn, which matches the "still runs in a year"
  bias.
- GitHub Pages deploy for MkDocs is a solved, well documented path.

If the team strongly prefers a JS toolchain or wants interactive schema exploration later,
Starlight is the fallback; the structure below is framework independent.

## 2b. Linear and Vercel style alternatives (aesthetic driven)

Raised because the team likes the Linear docs and Vercel docs look. Findings:

- Linear's docs (`linear.app/docs`, `linear.app/developers`) are a bespoke in house Next.js
  build. Not a public framework, not open source, not adoptable. The look is custom design
  work, not an installable theme.
- Vercel's own docs are also a custom internal Next.js app. What Vercel publishes for others
  is Nextra, their recommended docs starter. Nextra powers many sites with that same look
  (SWR, tRPC, Turborepo).
- So "the Linear/Vercel aesthetic" is not one framework. It is the modern dev docs layout
  (left nav, centered content, right TOC, dark mode, fast search) plus tight design tokens.
  Several frameworks give that off the shelf.

Closest installable matches:

- Fumadocs (Next.js): the most Linear/Vercel like of the installable frameworks; first party
  auto generation of reference pages; typed code blocks. Needs a Next.js runtime and some
  design effort. Best when hosted on Vercel. Static export to GitHub Pages is possible but
  more friction.
- Nextra v4 (Next.js): the battle tested Vercel look with the least design effort, since it
  is the Vercel ecosystem theme. App router plus RSC makes fully static GitHub Pages export
  more friction.
- Starlight (Astro): static first, deploys to GitHub Pages trivially, but you invest design
  effort to reach Linear level polish.
- Mintlify: hosted SaaS, very Linear like, but runs on their platform, not a free GitHub
  Pages self host.

Build from scratch: not recommended. From scratch means rebuilding search, nav, TOC, the
MDX pipeline, syntax highlighting, dark mode, responsive layout and accessibility, then
maintaining all of it. For a 31 page auto generated schema reference that is not worth it.
The Linear look is design tokens layered on one of the frameworks above, a fraction of the
effort with none of the maintenance tail.

The deciding fork is hosting, not looks. Our schemas are draft-07 component schemas, not
OpenAPI, so Fumadocs' headline auto gen feature does not directly apply; we write a small
generator either way, which levels the auto gen advantage across all options. That leaves:

- If we can host on Vercel: Fumadocs gets closest to the Linear/Vercel feel with the least
  fighting the framework.
- If GitHub Pages stays a hard requirement: Starlight is the clean static fit, themed toward
  Linear. Nextra also works but with static export friction.
- If aesthetic is secondary to zero maintenance: MkDocs Material stays the safe default.

Revised lean: Fumadocs on Vercel if hosting is flexible, otherwise Starlight on GitHub Pages.
Not from scratch. This supersedes the MkDocs lean above if the Linear/Vercel aesthetic is a
priority; see open question 8 (hosting) which now drives the framework pick.

## 3. Site structure and navigation

- Home / Overview
  - What the IDM is, why it exists (condensed from README), how to read a component page.
- Guides
  - Getting started: read a component page, find fields, units, required vs optional.
  - Authoring IDM JSON: how to build a valid instance (from `Creating IDM Product files`),
    validating against the schema, using the examples.
  - The common base and port model (from `docs/common.md`): measurement value shapes,
    identification, compliance, communication, environmental, mechanical, performance,
    files/images, metadata, system fields, and the AC/DC port model.
- Data model reference (auto generated, one page per component type)
  - 31 pages: battery, breaker, cable, capacitor, charger, combinerBox, contactor,
    converter, currentTransducer, diode, disconnect, fuelCell, fuse, generator, grounding,
    hvac, hydro, light, load, meter, motor, panel, powerDistributionUnit, precharge,
    rapidShutdownDevice, solar, transferSwitch, transformer, utility, voltageTransducer,
    wind.
  - Each page: hand written intro (reuse existing `docs/<type>.md`) followed by the
    generated field table (path, type, required, default, enum/allowed values, unit) and a
    link to the raw schema and the example instance.
  - An index/matrix page: type key, indicator (BAT, Q, PV, ...), plural, port configuration,
    link to page. This is a natural landing page for the reference section.
- Standards and ratings alignment
  - Document what the model actually references today: dcide-app validator alignment,
    Emerge Alliance, and the IEC vs UL short circuit rating fields on breaker and fuse.
  - Hold a placeholder for a fuller IEC 62683 mapping if you supply source material (see
    open question 1). I will not invent an IEC 62683 crosswalk.
- Changelog
  - Human readable notes per model change, seeded from git history of `schema/`. Optionally
    a generated schema diff between tags later.
- Contributing
  - Where the source of truth is (dcide-app validators), how schemas are regenerated, how
    to propose changes, docs build and preview steps, style rules (no em/en dashes, one
    bullet per line).

## 4. Schema to docs generation

Principle: the schemas are the source of truth; reference pages are generated, never hand
maintained field by field. Prose intros stay hand written.

Proposed flow:

- A generator script (Python, run before `mkdocs build`) reads each `schema/*.json` and its
  matching `examples/test<Type>.json`.
- For each type it emits a Markdown fragment: a flattened field table walking `properties`
  (resolving the local `$ref` reuse), capturing for each field its dotted path, JSON type,
  required flag, default, `const`/`enum` values, and unit (from the `unit` `const`/`default`
  or enum). Nested objects (environmental, mechanical, performance, port AC/DC blocks) are
  rendered as grouped sub tables.
- The generator combines the hand written intro (`docs/<type>.md`, minus the parts now
  generated) with the generated table into the final reference page, plus links to the raw
  schema and example.
- The common base is generated once from any component (the base is identical across types)
  or kept as the curated `common.md`; decision at build time.
- Options for the generator:
  - `json-schema-for-humans`: least code, produces per schema reference we embed.
  - Custom ~150 line walker: full control of table columns and units, tuned to this model.
  - Start with `json-schema-for-humans` to ship fast; swap to a custom walker if the output
    needs tighter formatting.
- The generator runs in CI on every build, so a validator sync that changes a schema
  updates the docs automatically. Generated Markdown is a build artifact and does not need
  to be committed (keeps diffs clean); we can commit it if we want previewable diffs.

Validation tie in (optional, recommended): a CI check that every `examples/test<Type>.json`
validates against `schema/<Type>.json`, so published examples are always valid.

## 5. Deployment

Target: GitHub Pages, built and deployed by GitHub Actions.

Recommended method: Pages from Actions (the official `actions/deploy-pages` flow), not the
legacy `gh-pages` branch. Reasons: no build artifacts committed to a branch, cleaner
history, first class support, and the site source stays only in the repo tree.

Workflow outline (to be added only after approval):

- Trigger: push to the base data model branch (and/or `main` once merged), plus
  `workflow_dispatch` for manual runs.
- Job build:
  - Checkout.
  - Set up Python, install MkDocs Material and the generator dependencies.
  - Run the schema to docs generator.
  - Optionally run the example validation check (fail the build if any example is invalid).
  - `mkdocs build` to `site/`.
  - Upload `site/` with `actions/upload-pages-artifact`.
- Job deploy:
  - `actions/deploy-pages`, with `pages: write` and `id-token: write` permissions and a
    `github-pages` environment.

Alternative: the `gh-pages` branch method (peaceiris/actions-gh-pages or `mkdocs gh-deploy`).
Simpler to reason about and works on older setups, but pollutes the repo with a build branch.
Recommend against unless the org standard requires it.

Repo settings the human must toggle (cannot be done from code):

- Settings > Pages > Build and deployment > Source: set to "GitHub Actions" (for the Pages
  from Actions method). If we instead use `gh-pages`, set Source to "Deploy from a branch"
  and pick `gh-pages` / root.
- Confirm the repo has Pages enabled and, if org policy restricts it, that Pages is allowed
  for this repo and visibility.
- If a custom domain is wanted, add it in Settings > Pages and set the DNS record; otherwise
  the site publishes at the default `github.io` URL.
- Confirm Actions is allowed to deploy Pages (default permissions include the `pages` and
  `id-token` scopes granted per workflow).

- Standards/alignment and contributing pages: ~0.5 day.
- Total: roughly 3 to 4 days of focused work for a solid first release, less if we accept
